# Skill: Code Review for Otedama

本スキルは、Otedamaに対するコードレビューの一貫した品質を確保するために、Claude Codeおよび人間レビュアーが参照すべき観点とチェックリストを定義します。レビューは機械的なルール適用ではなく、設計判断の妥当性評価を含む知的作業であり、本書はその判断を支援する基盤を提供します。

## レビューの目的

コードレビューは三つの目的を同時に達成します。第一に、バグと設計欠陥の早期発見です。第二に、コードベース全体の一貫性と可読性の維持です。第三に、レビューを通じた知識共有とコミュニティの育成です。これら三つの目的のうち、どれか一つが他を圧倒する状況は望ましくありません。バグ発見のみに偏れば機械的チェックに堕し、知識共有のみに偏れば技術的妥当性が損なわれます。

## レビュー観点の優先順位

レビューコメントは、以下の優先順位で提示します。高優先度の問題が存在する場合、低優先度の問題への指摘は控え、次回のラウンドに回します。一度に全ての問題を指摘すると、重要な修正が埋もれます。

最優先で確認する観点は**正確性**です。コードは意図通りに動作するか、境界条件は適切に処理されているか、同時実行時のデータ競合は存在しないか、メモリ安全性は確保されているかを確認します。次に確認する観点は**セキュリティ**です。入力検証は適切か、機密情報の漏洩経路はないか、暗号化処理は正しいか、権限昇格の経路はないかを確認します。特に資金に関わる領域——`internal/lightning/`および`internal/stratum/`のNoise NX関連ファイル（`noise*.go`）——への変更は、CODEOWNERS により所有者レビューを必須とします（**現状の CODEOWNERS が要求できるのは
メンテナ1名のレビューであり、「独立した二人以上」ではない**——session 266 に確認。
bus-factor 1 は `docs/solo-operations.md` 7.3 と `MAINTAINERS.md` が認めている既知の状態で、
二重レビューはレビュアーが増えた時点の目標である）（訂正 session 253: 本文はかつて`internal/security/`・`internal/auth/`を挙げていたが、両パスはCLAUDE.mdのアーキテクチャマップで「存在しないパス（作成禁止）」——セキュリティ関連コードは`lightning/`と`stratum/`に内包され、ZKP認証はv4.0スコープ。CONTRIBUTING.mdの同一是正=session 245と整合）。

その次の観点は**設計の妥当性**です。変更は`CLAUDE.md`の設計原則（Carmack・Martin・Pike）に従っているか、`CLAUDE.md`の禁止事項に抵触していないか、適切な抽象レベルで記述されているか、既存アーキテクチャとの整合性は保たれているかを確認します。**テストの充実度**も同時に確認します。新規機能には対応するテストが存在するか、エッジケースは網羅されているか、テストは意味のある検証をしているか（カバレッジ稼ぎではないか）を確認します。

最後の観点は**可読性と保守性**です。命名は適切か、コメントは「なぜ」を説明しているか、関数は適切なサイズか、公開APIにはgodocが付与されているかを確認します。これらは重要ですが、正確性・セキュリティ・設計の後に指摘します。

## チェックリスト

レビュー時に以下のチェックリストを順に確認します。チェックがスキップされる項目があれば、その理由をレビューコメントに記録します。

**正確性のチェック:** 関数の前提条件と事後条件は明示されているか。エラーは適切に処理されているか（`err != nil`の無視は明確に正当化されているか）。goroutineのライフサイクルは管理されているか（リークの可能性はないか）。context.Contextは適切に伝播されているか。time.Time、math/randなどの非決定的要素はテスト可能な形で注入されているか。

**セキュリティのチェック:** 外部入力は検証されているか。SQLインジェクション、コマンドインジェクション、パストラバーサルの可能性はないか。秘密情報（APIキー、秘密鍵、パスワード）がログ出力、エラーメッセージ、メトリクス、トレースに混入していないか。暗号化処理は標準ライブラリまたは監査済みライブラリを使用しているか（独自実装はないか）。TLSバージョンと暗号スイートは適切か。ZKP認証の実装は仕様通りか。

**設計のチェック:** 変更は既存のアーキテクチャ層の境界を尊重しているか。ハードウェア抽象化層、収益源コネクタ層、裁定エンジン層、決済層の依存方向が守られているか。循環依存は発生していないか。インターフェースは適切に分離されているか（Interface Segregation Principle）。依存は逆転されているか（Dependency Inversion Principle）。新規の抽象は既存の抽象で代替不可能な場合にのみ導入されているか。

**テストのチェック:** 変更箇所のテストカバレッジは低下していないか。エッジケース（空入力、nil、境界値、最大値、タイムアウト、エラー条件）は網羅されているか。テストは独立して実行可能か（他のテストへの依存がないか）。テストはフラキーでないか（時刻や乱数に依存していないか）。モックの使用は妥当か（過剰にモック化されていないか）。

**パフォーマンスのチェック:** ホットパスに不要なアロケーションは発生していないか。goroutineの数は制御可能か（無制限に生成されていないか）。チャネルのバッファサイズは適切か。データベースクエリはN+1問題を回避しているか。キャッシュは適切に使用されているか。

**ドキュメントのチェック:** 公開API（`pkg/`配下）の変更はgodocに反映されているか。破壊的変更は`CHANGELOG.md`に記録されているか。設定ファイル形式の変更はサンプル（`config.yaml.example`）に反映されているか。新機能はREADMEまたは関連ドキュメントに説明されているか。

## レビューコメントの書き方

レビューコメントは建設的で具体的であるべきです。問題の指摘だけでなく、可能な解決策を示唆することで、コントリビューターの学習を促進します。

良いレビューコメントは以下の構造を持ちます。第一に問題の明示（何が問題か）、第二に影響の説明（なぜ問題か）、第三に提案（どう修正できるか）、第四に参照（関連ドキュメントや類似コード）です。「これは間違っている」ではなく、「この関数は同時実行時にデータ競合を起こす可能性があります。具体的には、L42のマップ書き込みがロックされていません。`sync.RWMutex`を追加するか、`sync.Map`に置き換えることを検討してください。類似のパターンは`internal/arbitration/cache.go`を参照してください」というコメントが望ましい形式です。

指摘の深刻度を明示するプレフィックスを使用します。`[BLOCKING]`はマージ前に必ず修正が必要な問題、`[SUGGESTION]`は改善を推奨するが必須ではない提案、`[NITPICK]`は些細な改善点、`[QUESTION]`は動作の理解を確認する質問、`[PRAISE]`は優れた実装への称賛です。プレフィックスがあることで、コントリビューターが対応の優先順位を判断しやすくなります。

## 意見の相違の解決

レビュアーとコントリビューターの意見が相違する場合、以下の手順で解決します。第一に、技術的根拠を明示した議論を行います。「好みの問題」ではなく、「測定可能なトレードオフ」として議論を整理します。第二に、合意に達しない場合は、第三者（別のメンテナ）の見解を求めます。第三に、それでも合意できない場合は、メンテナが最終判断を下しますが、その判断理由をIssueまたはADR（Architecture Decision Record）として記録します。

レビュアーの指摘が常に正しいとは限りません。コントリビューターの側にも、技術的な正当性に基づいて異議を唱える権利があります。レビュープロセスは権威的ではなく、協調的な品質確保の場であるべきです。

## 特殊な領域のレビュー

セキュリティ関連のレビューは、本書のチェックリストに加えて、OWASP Top 10、CWE Top 25、Go specific vulnerabilities（gosecの検出項目）を参照します。暗号化関連の変更は、Cryptography Engineering（Ferguson, Schneier, Kohno）の原則に照らして評価します。

Lightning Network関連のレビューは、BOLT仕様（Basis of Lightning Technology）への準拠を確認します。LDKのバージョンアップによる影響も同時に評価します。Stratum V2関連のレビューは、stratumprotocol.orgの仕様書への準拠と、Stratum Reference Implementationとの相互運用性を確認します。

裁定エンジンのレビューは、アルゴリズムの正確性に加えて、数値計算の安定性（浮動小数点誤差、オーバーフロー、アンダーフロー）、予測モデルの妥当性、ポリシープリセットごとの期待動作を確認します。

## レビュー時間の目安

レビューに要する時間の目安は、変更行数に応じて以下の通りです。50行以下の小規模な変更は30分以内、50〜300行の中規模な変更は1〜2時間、300〜1000行の大規模な変更は半日から1日、1000行を超える巨大な変更は分割を依頼します。巨大なPRは品質の高いレビューが困難であり、小さな単位に分割することがコントリビューター側の責任です。

## 本スキルの更新

本スキルは実際のレビュー経験を通じて継続的に更新されます。見逃されたバグの類型、頻出する設計ミス、効果的だったコメントのパターンなどをフィードバックとして取り込み、四半期ごとに見直します。
