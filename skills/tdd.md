# Skill: Test-Driven Development for Otedama

本スキルは、OtedamaにおけるTDD（テスト駆動開発）の実践規律を定義します。TDDは単なるテストを先に書く技法ではなく、設計を駆動する思考方法です。Otedamaは資金とプライバシーを扱うソフトウェアであり、後付けのテストではなくテストから導かれる設計のみが、必要な信頼性水準に到達できます。

## なぜTDDか

本プロジェクトがTDDを採用する理由は三つあります。第一に、Otedamaの主要領域（Lightning決済、Stratum V2プロトコル、ZKP認証、裁定エンジン）は、テストなしでは正しさの検証が事実上不可能な複雑さを持ちます。後からテストを追加するアプローチでは、テストしにくい設計が放置され、バグが累積します。第二に、TDDは設計の質を上げます。テストから書き始めると、関数の境界、依存の方向、副作用の局在が自然に明確になり、Carmack・Martin・Pikeの三原則に整合する設計が強制されます。第三に、ソロ開発者とAIエージェントの協調開発において、テストは仕様書として機能します。人間が書いたテストをAIが満たす実装を生成し、AIが書いた実装を別のAIがレビューするサイクルにおいて、テストは共通言語になります。

## Red-Green-Refactorサイクル

TDDの中核は三段階サイクルです。各段階を飛ばすことは禁止され、全ての機能追加とバグ修正はこのサイクルに従います。

**Red段階**では、失敗するテストを最初に書きます。この時点で実装は存在しないか、不完全です。テストは明確に失敗し、失敗メッセージが「何が未実装か」を正確に示すべきです。Red段階の質は、テストの明確性で評価されます。テストが曖昧であれば、Green段階で通すコードも曖昧になります。テストの名前、アサーションメッセージ、入力データの選定全てに注意を払います。

**Green段階**では、テストを通す最小限のコードを書きます。この段階では美しさや効率を追求せず、ただテストを通すことだけを目的とします。意図的に「汚いコードで通す」ことが許され、むしろ推奨されます。この規律により、Refactor段階で何を改善できるかが明確になります。Green段階で過剰に設計すると、Refactor段階で行う改善が減り、設計能力が退化します。

**Refactor段階**では、テストが通り続けることを保ちながら、コードを改善します。重複の除去、命名の改善、関数の分割、抽象の導入、パフォーマンスの向上が対象です。Refactor段階を省略することが、最も頻繁な失敗パターンです。Green段階で書いた「動くが醜い」コードが、Refactorされずにmainブランチに取り込まれると、技術的負債が蓄積します。

三段階のサイクルは、一つの機能追加につき何度も繰り返されます。大きな機能を一度のサイクルで実装するのではなく、機能を小さな単位に分割し、各単位でサイクルを回します。経験的に、一サイクルは10〜30分程度が健全な範囲です。一時間を超えるサイクルは、機能分割が不十分であることを示します。

## テストの種別と使い分け

Otedamaでは五種類のテストを使い分けます。各種別は異なる目的を持ち、代替関係ではなく補完関係にあります。

**単体テスト**は最も頻繁に書かれるテストです。関数・メソッド単位の正常系と異常系を網羅し、外部依存はモックで置き換えます。単体テストは高速（ミリ秒単位）であり、開発中に継続的に実行されます。単体テストのカバレッジが90%以上であることが、Otedamaの最低基準です。単体テストは`*_test.go`ファイルで、対象ファイルと同じパッケージ内に配置されます。

**プロパティベーステスト**は、入力空間全体にわたる不変条件を検証します。単体テストが「特定の入力に対する特定の出力」を検証するのに対し、プロパティベーステストは「任意の入力に対して成立すべき性質」を検証します。裁定エンジンの配分決定（全ハードウェアへの配分合計が100%に等しい、配分比率は非負、切替コストが閾値を超える場合は切替が発生しない）、暗号化処理（暗号化→復号で元のデータが復元される、同じ入力を同じ鍵で暗号化しても異なる出力になる）、Lightning決済計算（送金額と手数料の合計は残高以下、送金後の残高は送金額と手数料の合計を引いた値に等しい）などに適用されます。Go 1.18以降のfuzz機能またはgopterライブラリを使用します。

**ファズテスト**は、パーサーとプロトコル実装に対する自動的な悪意ある入力生成です。Stratum V2メッセージパーサー、設定ファイルパーサー、API入力処理、Lightning TLV パーサーは全てファズテストの対象です。`go test -fuzz`で実行し、CI上で継続的に30秒から数分間実行します。ファズテストで発見されたクラッシュは、即座に修正すべき重大バグとして扱われます。

**統合テスト**は複数モジュールの連携を検証します。ハードウェア抽象化層と収益源コネクタ層の統合、裁定エンジンとハードウェア抽象化層の統合、Lightning Networkと決済層の統合などです。統合テストは`//go:build integration`タグで分離され、`make test-integration`で実行されます。単体テストより遅く（秒単位）、外部依存（テスト用のBitcoindノード、regtestのLightningノード）を実際に起動することがあります。

**E2Eテスト**はユーザーフロー全体を検証します。ダウンロードからマイニング開始、最初のshare送信、Lightning受領、ダッシュボード表示までの一連のフローを自動化します。`//go:build e2e`タグで分離され、`make test-e2e`で実行されます。E2Eテストは最も遅く（分単位）、最も壊れやすいため、主要なクリティカルパスに限定して数を絞ります。

## Otedama固有のテスト戦略

Otedamaの各領域には固有のテスト課題があり、一般的なTDDの指針を超えた具体的な戦略が必要です。

**Stratum V2プロトコル**のテストは、stratumprotocol.orgの公式仕様書のテストベクトルをgolden fileとして取り込みます。メッセージのエンコード・デコードについて、仕様書に記載された全てのテストベクトルに対する双方向変換テストを必須とします。独自のテストベクトルも追加しますが、公式テストベクトルへの準拠がまず優先されます。

**Lightning Network決済**のテストは、実ネットワークではなくregtestまたはSignetで行います。実mainnetでのテストは、開発中は資金損失リスクが高すぎます。LDKはregtest向けのテストハーネスを提供しており、これを活用します。統合テストでは、実際にチャネルを開き、送金し、決済を受領する全フローを検証します。E2Eテストでも同様ですが、頻度を絞ります。

**ZKP認証**のテストは、zkSNARK回路の正確性検証と、プロトコル全体の安全性検証を分離します。回路の正確性は単体テストで、プロトコルの安全性はプロパティベーステストで検証します。特に重要な不変条件として、「知識証明が成立しない場合、検証が必ず失敗する」「知識証明が成立する場合、検証が必ず成功する」「検証プロセスから秘密情報が漏洩しない」の三つがあります。

**裁定エンジン**のテストは、決定論的シミュレーションで行います。実際の収益期待値や切替コストを使用せず、テスト用の固定値を注入し、期待される配分決定を検証します。プロパティベーステストで、「期待収益が最も高い配分が選ばれる」「切替コストが期待収益差を超える場合は切替が発生しない」「配分の合計は常に100%である」などの不変条件を検証します。

**ハードウェア抽象化層**のテストは、実ハードウェアに依存しないモックデバイスで行います。モックは`Device`インターフェースを実装し、テストごとに挙動を注入可能とします。実ハードウェアでの動作検証は、統合テストまたはE2Eテストで限定的に行い、単体テストは常にモックを使用します。

## テストの書き方

良いテストは、以下の特徴を持ちます。実装の詳細ではなく振る舞いを検証する（内部のデータ構造ではなく外部から観測可能な結果をアサートする）。独立して実行可能である（他のテストへの依存がなく、任意の順序で実行できる）。決定論的である（時刻、乱数、ネットワーク状態に依存せず、常に同じ結果を返す）。高速である（単体テストは数ミリ秒、統合テストでも数秒以内）。失敗時のメッセージが診断的である（何が期待され、実際に何が起きたか、なぜ重要かが明示される）。

テスト関数名は`Test<対象>_<シナリオ>_<期待結果>`形式を推奨します。例えば`TestArbitrationEngine_EmptyPriceData_ReturnsError`、`TestLightningWallet_InsufficientBalance_RejectsPayment`のように、テスト名だけで何が検証されているかが理解可能な構造です。

テーブル駆動テストを積極的に使用します。Goの慣用句であり、複数シナリオを一関数で網羅できます。新しいシナリオの追加も容易です。

```go
func TestCalculateExpectedYield(t *testing.T) {
    tests := []struct {
        name     string
        price    float64
        hashrate float64
        power    float64
        want     float64
        wantErr  bool
    }{
        {"zero hashrate", 50000.0, 0, 1000, 0, false},
        {"negative price", -1.0, 100, 1000, 0, true},
        // ... more cases
    }
    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := CalculateExpectedYield(tt.price, tt.hashrate, tt.power)
            if (err != nil) != tt.wantErr {
                t.Fatalf("got error %v, wantErr %v", err, tt.wantErr)
            }
            if got != tt.want {
                t.Errorf("got %f, want %f", got, tt.want)
            }
        })
    }
}
```

## モックとインターフェース

テスタビリティは設計の成果です。テストしやすい設計は、必然的に疎結合で責務分離された設計になります。Otedamaでは、外部依存（ネットワーク、ファイルシステム、時刻、乱数、ハードウェア）は全てインターフェース経由で注入されます。

時刻依存は`Clock`インターフェースを介して注入します。`time.Now()`を直接呼び出すコードは、テストで時刻を制御できないためレビューで却下されます。

```go
type Clock interface {
    Now() time.Time
}

type realClock struct{}
func (realClock) Now() time.Time { return time.Now() }

type fakeClock struct{ now time.Time }
func (c *fakeClock) Now() time.Time { return c.now }
func (c *fakeClock) Advance(d time.Duration) { c.now = c.now.Add(d) }
```

乱数依存も同様で、`io.Reader`を受け取る設計にし、テスト時には決定論的なシードから生成されるリーダーを注入します。ネットワーク依存は`http.Client`を注入可能にし、テストでは`httptest.Server`を使用します。ファイルシステム依存は`fs.FS`インターフェースを活用し、テストでは`fstest.MapFS`を使用します。

## カバレッジの扱い

テストカバレッジは手段であり目的ではありません。90%以上のカバレッジを目標としますが、数値を稼ぐためにテストを増やすことは禁止します。カバレッジが低い箇所を発見したら、まずそのコードが本当に必要かを問います。必要であれば、意味のあるテストを追加します。意味のないテスト（getter/setterの機械的テスト、トリビアルな定数の比較）でカバレッジを水増しすることは、監査で指摘される対象です。

カバレッジは`go test -coverprofile`で計測し、`go tool cover -func`で関数単位の詳細を確認します。CIではカバレッジが前回コミットから大幅に低下した場合、警告を発します。
