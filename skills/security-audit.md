# Skill: Security Audit for Otedama

本スキルは、Otedamaのセキュリティ監査を体系的に実施するための基盤を提供します。Otedamaはユーザーの資金と暗号通貨鍵を扱うソフトウェアであり、セキュリティは機能ではなく前提です。本書は脅威モデル、監査手順、一般的な脆弱性カテゴリ、ツール活用を統合的に記述し、Claude Codeと人間監査者の両方が参照する基準書として機能します。

## 脅威モデル

Otedamaが直面する脅威を体系的に整理します。脅威を列挙することで、防御の優先順位が明確になります。

**資金関連の脅威.** 攻撃者がユーザーのLightning Network秘密鍵を取得する。攻撃者がユーザーのマイニング収益を自分のアドレスに誘導する。攻撃者がLightningチャネルを不正にクローズし、ユーザー残高を詐取する。攻撃者がプール接続を乗っ取り、ハッシュレートを盗む（プールハイジャック）。これらは金銭的損失に直結するため、最優先で防御します。

**プライバシー関連の脅威.** 攻撃者がユーザーのマイニング活動と実世界の身元を紐付ける。攻撃者がOtedamaのテレメトリ送信からユーザーの所在地や活動パターンを推定する。攻撃者がLightningペイメントの経路から取引相手を特定する。Otedamaの非カストディ・ZKP設計はこれらへの対抗を前提としています。

**可用性関連の脅威.** 攻撃者がOtedamaノードにDoS攻撃を仕掛け、マイニング収益を中断させる。攻撃者が依存ライブラリの脆弱性を悪用し、プロセスをクラッシュさせる。攻撃者が設定ファイルを破壊し、Otedamaを起動不能にする。これらは直接的な金銭損失にはつながりにくいですが、長期の機会損失を生じます。

**サプライチェーン関連の脅威.** 攻撃者がOtedamaのビルドプロセスに悪意あるコードを注入する。攻撃者が依存ライブラリの正規バージョンを悪意あるバージョンに置き換える。攻撃者がGitHub Actionsの権限を悪用し、リリースバイナリを改竄する。これらは広範なユーザーへの影響を持つため、検出は困難だが影響は甚大です。

**プラットフォーム固有の脅威.** 攻撃者がユーザーのマシンにマルウェアを送り込み、Otedamaのメモリから秘密鍵を抽出する。攻撃者が同一マシン上の他プロセスからOtedamaのメモリを読み出す。攻撃者がユーザーのブラウザ経由でOtedamaのWebインターフェースに不正アクセスする。これらはOS・ブラウザレベルの防御に一部依存しますが、Otedama側でも多層防御を採用します。

## 攻撃者のモデル

以下の攻撃者像を想定して設計と監査を行います。

**ネットワーク観測者.** ユーザーとプール、ユーザーと外部サービス間の通信を観測する能力を持つ攻撃者。内容の読み取りはTLSで防御されますが、メタデータ（接続先、通信量、タイミング）は観測可能です。

**悪意あるサーバー運営者.** ユーザーが接続するマイニングプール、AI推論マーケットプレイス、Lightningサービスプロバイダが悪意を持つ場合。Otedamaは非カストディ設計により、これらのサーバーが悪意を持っても直接の資金流出は起こらない設計を目指します。

**悪意あるプラグイン作者.** Otedamaのプラグイン機構を利用して悪意あるコードをユーザー環境で実行する攻撃者。サンドボックス化された実行環境と、公式認証プラグインとの区別が防御の基盤となります。

**国家レベル攻撃者.** 大規模な計算資源と長期的な執着を持つ攻撃者。全ての脅威に対して完璧な防御は不可能ですが、高コストな攻撃を強いる設計を目指します。

## 監査の基本手順

新規コードまたは既存コードの監査は以下の手順で実施します。手順の省略は重大な見落としを生むため、時間的制約がある場合でもスコープを縮小して全手順を実行します。

**第一段階：コンテキスト理解.** 監査対象のコードが何を達成しようとしているか、どの脅威モデルに対処しようとしているかを理解します。Issue、PR説明、関連ドキュメント、ADRを読みます。コードの意図を理解せずに監査を始めると、「コードは正しく動作するが意図と異なる動作をする」という最悪の見落としが発生します。

**第二段階：自動ツールによる走査.** `gosec`、CodeQL、Semgrep、`govulncheck`を順次実行し
（**`govulncheck` だけは CI に無く、手元で走らせる必要がある**——session 266 に確認、
`docs/KNOWN_LIMITATIONS.md` §21）、既知の脆弱性パターンと依存ライブラリの脆弱性を検出します。これらのツールは偽陽性を含むため、全ての警告を機械的に修正するのではなく、各警告の妥当性を個別に評価します。偽陽性と判断した場合、その理由をコメントとして記録します。

**第三段階：手動コードレビュー.** 以下の観点で手動レビューを行います。入力検証の完全性（境界条件、型、形式、意味的妥当性）、エラー処理の網羅性（失敗経路での秘密情報漏洩、エラーメッセージ経由の情報漏洩）、並行処理の正確性（データ競合、デッドロック、リソースリーク）、暗号化処理の適切性（適切なライブラリ使用、正しい操作順序、鍵管理）、時刻依存の安全性（タイミング攻撃、replay攻撃、有効期限の処理）。

**第四段階：動的テスト.** ファズテストを該当領域に適用します。Stratum V2メッセージパーサ、設定ファイルパーサ、API入力処理など、外部入力を処理する箇所は全てファズテストの対象です。`go test -fuzz`を使用します。**ただし CI でファズを回すジョブは存在しない**（session 266 に確認）——
fuzz target は `internal/stratum/frame_fuzz_test.go` に2本あるが、通常の `go test` では
シードコーパスを実行するだけで新しい入力を探索しない。継続実行するには §21 の是正が要る。プロパティベーステストも同時に活用し、暗号化処理や裁定エンジンの数理的性質を検証します。

**第五段階：統合的評価.** 個別の問題だけでなく、複数の問題が組み合わさった際の攻撃経路を検討します。単独では些細な情報漏洩が、他の脆弱性と組み合わさることで重大な攻撃経路を形成することがあります。脅威モデルの各項目に対して、現在の防御が十分かを問い直します。

**第六段階：文書化.** 監査の発見事項、評価、推奨対応を文書化します。ブロッキング（マージ前に必須修正）、推奨（修正を推奨するが必須ではない）、情報提供（将来の改善のための記録）の三段階で優先度を付けます。報告書は該当PRのコメントまたはセキュリティIssueに記録します。

## 頻出の脆弱性カテゴリ

Otedamaのコンテキストで特に注意すべき脆弱性カテゴリを列挙します。

**秘密情報のログ出力.** 秘密鍵、API キー、パスワード、シード、ノードID（場合による）がログ、エラーメッセージ、メトリクス、トレースに混入するパターン。`fmt.Sprintf("%+v", config)`のような全フィールド出力は特に危険です。秘密情報を含む型には`String()`メソッドをオーバーライドして`[REDACTED]`を返すように実装します。

**タイミング攻撃.** パスワード比較、署名検証、MACの比較で通常の`==`演算子や`bytes.Equal`を使用するパターン。実行時間が入力依存であるため、攻撃者が時間測定で秘密を推測できます。`crypto/subtle.ConstantTimeCompare`を使用します。

**不適切な乱数生成.** `math/rand`を暗号用途に使用するパターン。`math/rand`は予測可能であり、セッショントークン、ノンス、鍵生成には使用できません。`crypto/rand`を使用します。

**SSRF（Server-Side Request Forgery）.** ユーザー入力からURLを構築し、HTTPリクエストを送るパターン。内部サービス（`localhost`、`169.254.169.254`など）へのアクセスが可能になります。URLの検証と、明示的なallowlistの使用が必要です。

**XXE、XSS、SQLインジェクション.** Web管理インターフェース（`web/`配下）で特に注意します。テンプレート自動エスケープ、パラメータ化クエリ、XML外部エンティティ解決の無効化が基本的な防御です。

**goroutineリーク.** goroutineが終了条件なしに起動され、プロセスライフタイムで蓄積するパターン。長時間稼働するOtedamaでは致命的です。`context.Context`によるキャンセル伝播、`sync.WaitGroup`による完了待機、`defer`による確実なクリーンアップを徹底します。

**依存ライブラリの脆弱性.** `govulncheck`で検出される脆弱性に加え、transitiveな依存の監査も定期的に実施します。依存グラフは小さく保ち、不要な依存は削除します。

**Lightning Network固有の脆弱性.** チャネル状態の不整合、古い状態のブロードキャスト、watchtowerの設定漏れ、HTLCタイムアウトの誤処理。LDKのドキュメントとBOLT仕様を参照して、Otedamaの利用方法が想定範囲内であることを確認します。

**Stratum V2固有の脆弱性.** 暗号化されていないチャネルでのshare hijacking、不正なJob Negotiationによるブロック改竄、偽のwork template受理。仕様書の「Security Considerations」セクションを熟読し、Otedamaの実装がそれらに対処していることを確認します。

## ツールの統合使用

以下のツールを組み合わせて使用します。各ツールは異なる種類の問題を検出するため、単一ツールへの依存は避けます。

**gosec.** Go固有のセキュリティ問題を検出します。`gosec -severity medium ./...`で実行し、明らかな問題（秘密情報のハードコーディング、`math/rand`の暗号用途、危険な権限設定など）を検出します。

**CodeQL.** GitHub Advanced Securityの一部として提供されるセマンティック分析ツール。データフロー分析によってSSRF、SQLインジェクション、パストラバーサルなどを検出します。`.github/workflows/codeql.yml`で定期実行を設定します。

**Semgrep.** パターンベースの静的解析ツール。Otedamaのコンテキスト固有のルール（例：「`log.Printf`に`privateKey`を渡してはならない」）をカスタムルールとして追加します。

**govulncheck.** Go公式の脆弱性スキャンツール。依存ライブラリに既知の脆弱性がないかを確認します。
`govulncheck ./...` を CI で毎回実行する——**というのが目標で、現状はどのワークフローにも存在しない**
（session 266 に確認。§21）。監査時は手元で実行し、結果を記録すること。

**fuzz testing.** Go 1.18以降の標準機能。パーサー、プロトコル実装、入力処理に対して継続的に適用します。

**trivy.** Dockerイメージとコンテナの脆弱性スキャン。`trivy image otedama:latest`で実行します。

**scorecard.** OpenSSF Scorecardでプロジェクト全体のセキュリティ姿勢を定期評価します。

## 特定領域の監査深度

以下の領域は通常より深い監査を要求します。

（訂正 session 253: 本節はかつて`internal/security/`・`internal/auth/`・`internal/plugin/`という、CLAUDE.mdのアーキテクチャマップで「存在しないパス（作成禁止）」と明記された領域を列挙し、また`internal/lightning/`について未実装のLDK決済・BOLT準拠・mainnet決済テストを必須要件として記述していた。以下は実在する領域と現状の実装範囲に是正した記述。CONTRIBUTING.md=session 245／code-review.md=session 253の同一是正と整合。）

**`internal/lightning/`.** 現状の実装範囲はBIP-39シードの生成とAES-256-GCMによる暗号化保管のみ（`seed.go`/`seedstore.go`/`wallet.go`）。Lightningノード・チャネル・決済ルーティングは未実装（v3.6以降、ADR-007）。資金の直接流出に繋がり得るため、CODEOWNERSにより二重レビュー必須。現時点の監査重点は、シードが端末外へ出ない構造の保全、at-rest暗号（scrypt+AES-GCM）の正しい使用、atomic writeによるウォレットファイル破損防止、そして**リカバリフレーズがユーザーに確実に一度提示されること**（session 253で`engine.printRecoveryPhrase`として実装。ここが欠けると非カストディの約束が実質的に破綻するため、監査項目として重視する）。将来LDK等の決済機能が入る際は、API使用方法の厳密なレビュー・BOLT仕様準拠・実ネットワーク（Signetまたは小額mainnet）挙動テストをその時点で必須要件に加える。

**`internal/stratum/`のNoise NX関連（`noise*.go`）.** SV2トランスポート暗号化を含む資金・プライバシー隣接領域。CODEOWNERSにより二重レビュー必須。暗号プリミティブ（ChaCha20-Poly1305等）の使用が正しいか、ハンドシェイク状態機械が仕様（sv2-spec 04章）通りか、nonce管理・鍵導出（HKDF）に破綻がないか、サイドチャネル耐性があるかを確認する。現状はNoise NXが実接続に未配線（既定は平文SV2、KNOWN_LIMITATIONS §2）である点に留意。

**（参考）v4.0スコープの未実装領域.** ZKP認証（かつて`internal/auth/`として記述されていたが未存在・v4.0スコープ）が実装される際は、暗号プリミティブの正しさ・プロトコル仕様準拠・サイドチャネル（タイミング/電力/キャッシュ）耐性を監査観点に加える。プラグイン機構（かつて`internal/plugin/`として記述されていた）はROADMAP「削除されたマイルストーン」で明示的に却下済みであり、監査対象として想定しない。

これらの領域に対するPRは、自動テストと静的解析に加えて、人間による深い思考を要求します。急いでマージすることは許されず、十分な時間を確保して監査します。

## セキュリティインシデント対応

脆弱性が発見された場合、`SECURITY.md`に定められた手順に従います。本スキルは発見プロセスを扱いますが、発見後の対応プロセスは`SECURITY.md`を参照します。本スキルで監査した結果、脆弱性を発見した場合は、公開のIssueを作成せず、Private Vulnerability Reportingまたはメンテナへの直接連絡を使用します。

## 本スキルの更新

本スキルは実際の監査経験、新しい脅威の出現、セキュリティ研究の進展を反映して継続的に更新されます。特に以下のタイミングで見直します。新しいタイプの脆弱性が発見された場合、既存の防御が突破された場合、新しいセキュリティツールが登場した場合、Otedamaのアーキテクチャに重大な変更があった場合。
