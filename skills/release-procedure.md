# Skill: Release Procedure for Otedama

本スキルは、Otedamaの新規バージョンをリリースする際の手順を体系化したものです。リリースは単なるバージョン番号の更新ではなく、ユーザーとの信頼関係を構築する重要な儀式です。手順の標準化により、リリースの品質と安定性を確保し、メンテナのリリース作業負担を軽減します。

> **本書の性質（session 266 で明記）。** 以下は**目標手順**であり、現状の自動化の記述ではありません。
> 実際に走るのは `.github/workflows/release.yml` のクロスビルドと GitHub Releases への添付だけです。
> 本書が「自動化されています」と書いていた次の各項目は**存在しません**——
> GPG/cosign 署名、SBOM、Docker Hub 公開（実際は ghcr.io）、Homebrew/Snap/AUR への展開、
> チェックサム公開（`docs/KNOWN_LIMITATIONS.md` §21。修正済みワークフローは §13 に貼り付け可能な形で用意済み）。
> チェックリスト中の実行不能な項目も同様に印を付けた。**リリース手順書が実在しない自動化を前提にすると、
> 手順を踏んだつもりで踏めていないリリースが出る**——それが本書で最も高くつく欠陥である。

## リリースの種類

Otedamaは以下の三種類のリリースを定義します。メジャーリリース（v3.0.0、v4.0.0など）は、破壊的変更を含むリリースで、年に最大1〜2回程度を想定します。マイナーリリース（v3.1.0、v3.2.0など）は、後方互換性を保ちつつ新機能を追加するリリースで、四半期ごとを目安とします。パッチリリース（v3.0.1、v3.0.2など）は、セキュリティ修正とバグ修正のみを含むリリースで、必要に応じて随時行います。

Semantic Versioningに厳密に従います。破壊的変更が一つでも含まれる場合はメジャーバージョンを上げ、新機能の追加のみの場合はマイナーバージョンを、バグ修正のみの場合はパッチバージョンを上げます。プレリリース（アルファ、ベータ、リリース候補）は`v3.0.0-alpha.1`、`v3.0.0-beta.2`、`v3.0.0-rc.1`の形式で命名します。

## リリース前チェックリスト

リリースタグを打つ前に、以下のチェックリストを全て完了させます。一つでも未完了の項目がある場合、リリースを延期します。

**コード品質:** `golangci-lint run`が警告ゼロで完了していること。`go test ./...`が全プラットフォームで成功していること。テストカバレッジが目標値（v3.0.0時点で85%、v3.0.0以降で90%）を満たしていること。`gosec`、CodeQL、Semgrep、`govulncheck`の全セキュリティスキャンが警告なしで完了していること。

**ドキュメント:** `README.md`が最新機能を反映していること。`CHANGELOG.md`に当該バージョンの変更内容が記載されていること。破壊的変更がある場合、`docs/MIGRATING-FROM-V2.md`に移行手順が記載されていること。内部パッケージのgodocが最新であること。主要10言語のドキュメントが更新されていること——**ただし現状ドキュメントは日英のみ**であり、
10言語あるのは `internal/i18n/messages/` の起動時ログ15メッセージのカタログである。
この項目は達成不能なまま放置せず、範囲を「日英ドキュメント＋カタログの完全性テスト」に改めるか、
翻訳体制を用意するかの判断が要る（`docs/CATEGORY_AUDIT.md` の改善点 #7）。

**バージョン情報:** `VERSION`ファイルが新バージョンに更新されていること。`go.mod`のモジュールパスが変更されていないこと（メジャーバージョン2以上の場合は適切なパス変更があること）。ソースコード内のバージョン定数（`internal/version/version.go`）が更新されていること。

**依存関係:** `go mod tidy`が実行され、不要な依存が削除されていること。`go mod verify`が成功していること。依存ライブラリに既知の脆弱性がないこと（`govulncheck ./...`で確認）。ライセンス互換性が維持されていること（`go-licenses check ./...`などで確認）。

**テスト:** ユニットテスト、統合テスト、E2Eテストの全てが通過していること。負荷テストで性能退行がないことを確認（前バージョンとのベンチマーク比較）。~~v2からの移行テスト（`otedama migrate-from-v2`）~~ — **そのサブコマンドは存在しない**（session 266 に確認。
ディスパッチャは run/version/config/service/doctor/wallet/completion/help のみ）。移行は
`docs/MIGRATING-FROM-V2.md` の手作業手順であり、自動移行コマンドを作るか、この項目を落とすかの判断が要る。

**プラットフォーム確認:** Windows（x86_64）、macOS（x86_64、ARM64）、Linux（x86_64、ARM64）の各プラットフォームでのビルドとスモークテストが成功していること。Dockerイメージが正常にビルドされ、起動すること。
（**FreeBSD はリリース対象ではない**——`release.yml` のマトリクスに無く、実機テストもしていない。
クロスコンパイルが通ることのみ確認済み。§ `README.md` の必要環境を参照。）

## リリース手順

チェックリスト完了後、以下の手順でリリースを実行します。

**第一段階：リリースブランチの作成.** mainブランチから`release/v<version>`ブランチを作成します。このブランチ上で最終的なバージョン更新コミットを作成します。バージョン番号の更新、CHANGELOG.mdへの日付追加、リリースノート草稿の作成を含めます。

**第二段階：リリースノートの作成.** `docs/releases/v<version>.md`として詳細なリリースノートを作成します。リリースノートは以下の構成を持ちます。冒頭サマリー（日本語と英語の両方で、このリリースの意義を1〜2段落で説明）、新機能（ユーザー視点での機能説明と使用例）、変更点（既存機能の改善や挙動変更）、バグ修正、破壊的変更（該当する場合、詳細な移行手順）、セキュリティ修正（CVE番号があれば記載）、貢献者への謝辞、既知の問題、次回リリースへの展望。

**第三段階：タグ作成と公開.** リリースブランチをmainにマージ後、GitHubでタグ`v<version>`を作成します。タグメッセージはリリースノートの冒頭サマリーを含めます。`git tag -s v<version> -m "Release v<version>"`のようにGPG署名付きタグを使用します。タグのプッシュ（`git push origin v<version>`）がGitHub Actionsのリリースワークフローをトリガーし、自動的にバイナリビルドとGitHub Releasesへの公開が行われます。

**第四段階：バイナリ配布.** GitHub Actionsがクロスプラットフォームバイナリをビルドし、GitHub Releasesに添付します。
**現状ここまでが実際に動く範囲**で、添付されるのは `.tar.gz` のみです。以下は**未実装**（§21）:

- SHA-256 チェックサム（`checksums.txt`）— **`install.sh` はこのファイルを必須としており、
  無いために文書化された一行インストールは必ず中断する。** 修正済み `release.yml` が §13 にある。
- GPG/cosign 署名、SBOM — ワークフローに1件も存在しない。
- コンテナ公開先は **Docker Hub ではなく ghcr.io**（`ci.yml` の `DOCKER_REGISTRY`）。
  当該タグが実際に公開されているかは本環境からは確認できない（ghcr.io は egress ブロック）。

**第五段階：配布チャネルへの展開.** — **現時点では該当なし。** Homebrew / Snap / AUR への展開は
**自動化されていません**（session 266 に確認: `snapcraft`・AUR に関する記述はワークフローに0件。
`release.yml` の `update-homebrew` ジョブは他リポジトリを `GITHUB_TOKEN` でチェックアウトしようとしており、
そのトークンは他リポジトリに対して認証できないため、動作したことはない）。
バイナリハッシュの掲載も、そもそもチェックサムが公開されていないため実施できない。
これらを行うなら、まず §13 の `release.yml` を適用してチェックサム公開から始める。

**第六段階：アナウンス.** リリース後、以下のチャネルでアナウンスを行います。GitHub Discussionsへのリリース投稿、X（旧Twitter）での告知（日本語と英語）。
（**Discord は採用しない**——`docs/solo-operations.md` 4.1 が「リアルタイムチャットは非同期OSS開発の最大の
時間泥棒であり、ソロメンテナのバーンアウトを最速で引き起こす」として明示的に不採用としている。
本書が「公式Discordサーバー」を前提にしていたのは2文書間の矛盾で、session 266 に不採用側で解消した。
メーリングリストも存在しない。）プレリリース版ではなく正式リリース版の場合、HackerNews、Reddit（r/Bitcoin、r/BitcoinMining、r/selfhosted、r/golang）への投稿も検討します。日本市場向けにはZennとQiitaでの技術記事も同時公開します。

## リリース後の対応

リリース直後の24〜72時間は、特に注意深く監視します。GitHub Issuesで報告される新規バグ、Discordでのユーザーからの問い合わせ、各種メトリクス（GitHub Releases のダウンロード数）を定期的に確認します。
（**クラッシュレポートとテレメトリは存在しない。** Otedama は一切 phone home しない設計であり
（`docs/SUSTAINABILITY.md` §7）、送信するコードも収集先も無い。監視できるのは公開 API から見える数字だけである。）緊急の問題が発見された場合、以下の判断を迅速に行います。

軽微な問題の場合、次回のパッチリリースに修正を含めます。重大な問題の場合、リリースを一時的に取り下げ（GitHubリリースを削除、Dockerイメージをyank、distributionチャネルから取り下げ）、修正版をすぐにリリースします。セキュリティ脆弱性の場合、`SECURITY.md`の手順に従い、CVE採番と責任あるディスクロージャーを並行して進めます。

## リリース頻度の方針

リリース頻度はOtedamaの成熟度に応じて調整します。アルファ段階では月次または隔週で新規プレリリースを公開し、フィードバックサイクルを高速化します。ベータ段階では2〜4週間ごとのプレリリース更新を目指します。正式リリース以降は、マイナーリリースを四半期ごと、パッチリリースを必要に応じて、メジャーリリースを12〜18ヶ月ごとに行います。

「リリースのためのリリース」は避けます。内容のない定期リリースは、ユーザーの更新疲れを招き、重要なリリースへの注意を散漫にします。リリースするだけの価値がある変更が蓄積された時点で、適切なバージョン区分でリリースします。

## サポート期間

各リリースのサポート期間は以下の通りです。最新メジャーバージョン（現時点でv3.x）は全てのセキュリティ修正を提供します。一つ前のメジャーバージョン（v2.x）は、次期メジャーバージョンのリリースから6ヶ月間、重大なセキュリティ修正のみを提供します。それ以前のバージョンはサポートされません。プレリリース版（アルファ、ベータ、RC）は正式リリース版への移行を推奨し、プレリリース版固有のサポートは提供しません。

この方針はユーザーへの約束であり、サポート期間の短縮は行いません。期間の延長は必要に応じて検討します。

## リリースプロセスの改善

リリースプロセスは継続的に改善します。各リリース後、リリース担当者（メンテナ）は以下をふりかえります。予定通りにリリースできたか、想定外の問題が発生しなかったか、プロセスのどこが非効率だったか、自動化可能な手作業が残っていないか。これらのふりかえりは`docs/release-retrospectives/`配下に記録し、次回以降のリリースプロセス改善に活用します
（同ディレクトリは未作成——最初のふりかえりを書くときに作る）。

理想的なリリースプロセスは、`git tag`を打つ以降の全作業が自動化され、メンテナが介入する必要がない状態です。この理想に近づくための投資は、長期的に大きな時間節約となります。

## 本スキルの更新

本スキルは実際のリリース経験を通じて継続的に更新されます。各リリース後のふりかえりから得られた改善点は、本書に取り込まれます。
