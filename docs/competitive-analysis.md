# Competitive Analysis: Mining Software Landscape in 2026

本書は、Otedamaが参入する市場の既存プレイヤーを体系的に分析し、Otedamaが埋めるべき空白を特定するものです。分析対象は家庭用から業務用までのマイニングソフトウェア七製品であり、各製品の長所と短所を並置することで、設計判断の根拠を外部からも検証可能な形で記録します。本分析は執筆時点（2026年）のスナップショットであり、市場変化に応じて見直します。
**競合各製品について本書が述べる性能・料金・対応範囲は、各社の公表情報に基づく要約であり、
Otedama 側で計測・検証したものではありません**（Otedama 自身についての記述は、
session 266 以降すべて実装への参照つきで書かれています）。

## 分析対象と分類

競合を三カテゴリに分類します。第一カテゴリは**技術者向けCLIツール**で、CGMinerとBFGMinerが該当します。第二カテゴリは**簡易マーケットプレイス型**で、NiceHashとKryptexが該当します。第三カテゴリは**プロ向け管理プラットフォーム**で、Awesome Miner、Hive OS、Braiins OS+が該当します。

この三分類は、ユーザーの技術習熟度と運用規模の二軸で切り取った結果であり、完全ではありません。Cudo Miner、MultiMiner、EasyMiner、lolMiner、minerstatなど他の製品も存在しますが、上記七製品が市場認知と実装水準の両面で代表例として妥当と判断しました。

## CGMiner：業界標準の歴史的遺産

CGMinerは2011年以降のビットコインマイニングコミュニティにおける事実上の標準実装です。Cで書かれ、Linux・Windows・macOS・Raspberry Pi・OpenWrtルーターで動作し、SHA-256、Scrypt、その他多数のアルゴリズムに対応します。強みは圧倒的な成熟度、既存のほぼ全てのASIC・FPGAとの互換性、極めて低いリソース使用量、オープンソースとしての透明性です。

弱みは深刻であり、「CGMinerは純粋なCLIツールであり、多数の機能と設定を制御する必要がある状況で、純粋なコマンドラインインターフェースはCGMinerの挙動制御を非常に困難にする」という構造的問題を抱えています。初心者にとってのセットアップ難易度は極めて高く、プール設定、ワーカー名、パスワード、API設定、failoverロジック、difficulty、intensity、gpu-engine、gpu-memclockなど数十のパラメータを理解しなければまともな運用ができません。GUIは一切なく、ダッシュボードは一切提供されません。Stratum V2対応は不完全で、Lightning Network決済は対応外です。最終更新は活発ではなく、近年のStratum V2エコシステムとの整合性は失われつつあります。

CGMinerの存在は、Otedamaにとって「技術者向けツールの空きニッチはほぼ存在しない」ことを示唆します。この領域での競争は無益であり、Otedamaは別の層でポジションを取るべきです。

## BFGMiner：モジュール式の老舗

BFGMinerはCGMinerのフォークとして2012年に始まり、その後独自の進化を遂げました。動的クロッキング、リモート管理インターフェース、多様なデバイスドライバーを特徴とします。モジュール式アーキテクチャはCGMinerより柔軟です。

弱みはCGMinerと類似しています。「BFGMinerは機能性を美しさより優先しており、それがユーザーインターフェースに反映されている。急な学習曲線、限定的なユーザーフレンドリーインターフェース、包括的ドキュメントの欠如は、特に暗号通貨マイニングの新参者にとって困難をもたらす可能性がある」と要約されます。さらに深刻な問題として、BFGMiner、SGMinger、CGMinerを対象としたCVE-2014-4501、CVE-2014-4502、CVE-2014-4503の三つの脆弱性（スタックバッファオーバーフロー、ヒープメモリ破壊、中間者攻撃による認証情報の平文漏洩、client.reconnectメッセージによる悪意あるプールへの誘導、リモートコード実行）が報告されています。これは、Otedamaが第一フェーズから採用する三層セキュリティレビュー（自動スキャン、AIレビュー、人間レビュー）の正当性を実証的に裏付けます。

## NiceHash：簡易さの代償としてのカストディリスク

NiceHashは2014年開始の、ハッシュレート売買マーケットプレイスです。採掘者は自分の計算力を売り、買い手は他の仮想通貨を採掘するためにそれを借ります。強みは初心者向けの自動プロフィット切替、ワンクリックの参入、マルチハードウェア対応、統合ウォレットです。

深刻な弱みが三つあります。第一に、2017年に4,700 BTC（当時約6,200万ドル）が流出した大規模ハッキング事件の歴史を持ちます。現在はKYC、2FA、ウォレットホワイトリストが強化されていますが、中央集権的な預かり構造そのものが構造的リスクであり、これを完全に除去することはできません。第二に、プラットフォーム手数料が2〜5%と高く、ビットコイン以外の仮想通貨での受取には変換が必要です。第三に、KYCが必須であり、プライバシーを重視するユーザーは使用できません。

NiceHashの存在は、Otedamaが非カストディ設計とZKP認証を主軸に据える戦略の妥当性を強く支持します。「簡易さ」の価値は認めるが、その実現がカストディと引き換えになっている現状に、明確な市場空白があります。

## Kryptex：Windows特化の簡易ツール

Kryptexはロシア開発のWindowsデスクトップアプリで、家庭PCのCPU・GPUを使った小規模マイニングに特化しています。強みは5分以内のセットアップ、自動的に最も利益の出るコインを選択する自動切替、低い最小出金額（$0.5）、ビットコイン・法定通貨・ギフトカードでの受取選択肢です。

弱みとして、Windows専用でmacOSとLinuxで使用できない、引き出し手数料が比較的高く小規模マイナーの利益を減少させる、リソース集約的でハードウェア消耗と電気代の上昇を招く可能性がある、セキュリティリスクがあり特に定期更新されない場合はマルウェア感染リスクがある、市場状況に利益が大きく依存し変動的といった問題があります。Bitcoinとイーサリアム系のProof-of-Workの対応のみで、マイニングプール選択の透明性は低く、プールは運営者指定です。

Kryptexの存在は、「Windows家庭ユーザー向けの簡易ツール」という狭いセグメントでの競争激化を示します。Otedamaはクロスプラットフォームとプール選択の透明性で差別化可能です。なお実際のリリース対象は
linux/amd64・linux/arm64・darwin/amd64・darwin/arm64・windows/amd64 の5つで（`.github/workflows/release.yml`）、
**FreeBSD ビルドは提供していません**（`SUSTAINABILITY.md` §8 では Tier-2 候補として挙がっていますが、
現時点では候補です）。

## Awesome Miner：プロ向け管理プラットフォーム

Awesome Minerは2014年からIntelliBreeze社が提供するWindows/Linux向けの管理ツールです。中央集権ダッシュボードで複数のマイニングリグを監視・制御でき、ASIC・GPU・CPU・FPGAに対応します。強みは大規模ファーム向けの集中管理、プロフィット切替、豊富なハードウェア対応、デジタル署名済み実行ファイルとアンチウイルススキャンによるセキュリティ配慮です。

弱みは家庭ユーザー向けではなく、「小規模で始めて大規模に育てる」タイプのユーザーを前提にしていることです。ダッシュボードの学習コストは高く、無料版は機能制限があり、本格活用には有料ライセンスが必要です。Stratum V2対応とLightning Network決済は組み込まれておらず、カストディ型の決済モデルに依存します。

## Hive OS：Linux専用OSとしてのマイニング環境

Hive OSはマイニング専用のLinuxディストリビューションで、リグを起動すれば即座に管理ダッシュボードに統合されます。Flight Sheetsでプール・ウォレット・コインの組み合わせを即座に切り替え可能、GPUオーバークロックプロファイルのカスタマイズを数秒で全ファームに適用可能など、業務用マイニングファームに最適化されています。

弱みは、Hive OSの専用Linuxディストリビューションをインストールする必要があり、既存OS環境で使用できないことです。家庭ユーザーが既存のWindows PCやMacbookで気軽に試すことはできません。料金は月額制で、小規模ユーザーには費用対効果が低くなります。

## Braiins OS+：Stratum V2先進実装の制限

Braiins OS+は、Stratum V2プロトコルの実装で業界を先導するBraiins社が提供するASIC用カスタムファームウェアです。強みはS17、S17 Pro、S17+、S17e、T17、T17+、T17e、S9でのハッシュレート向上（最大25%）と、per-chipチューニングによる電力効率改善、Slush Poolでの0%手数料、Stratum V2完全対応、オートチューニング、バッチ設定・リモート監視です。

弱みは三つあります。第一に、英語のみサポートで、日本語・中国語・スペイン語などへのローカライズは皆無です。これはグローバル市場への障壁です。第二に、対応ASICモデルが限定的（Antminer S17/T17シリーズ中心、S19系列の対応は製品ラインによって異なる）で、GPUやCPUには対応しません。第三に、ファームウェアのフラッシュという技術的作業が必要で、初心者には敷居が高い上、「インストール/アンインストールの困難さ」は初期リリース時から繰り返し指摘されてきた問題です。

## 共通する弱点：Otedamaが埋める空白

七製品を横断的に分析すると、Otedamaが埋めるべき五つの共通弱点が明確になります。

**第一の空白は、ゼロ設定のクロスプラットフォーム体験**です。CGMiner・BFGMinerはCLIで高難易度、KryptexはWindows専用、Hive OSは専用Linux、Braiins OS+はASIC限定です。「既存の任意のOS上で、設定なしで5分以内に稼働する」製品は事実上存在しません。Otedamaはこの空白に入ることで、新しいユーザー層（技術に深く関わりたくないが既存ハードウェアから収益を得たい層）を開拓できます。

**第二の空白は、非カストディ・ZKP認証の簡易製品**です。NiceHashは簡易だがカストディ、CGMinerは非カストディだが難解、Kryptexは簡易だがプライバシー面で不透明です。「簡易かつ非カストディ、KYC不要」の組み合わせは市場に存在せず、規制強化が続く2026年の環境下では戦略的価値が高いポジションです。

**第三の空白は、多言語ネイティブサポート**です。Braiins OS+、Hive OS、Awesome Miner、CGMinerは実質英語のみ、Kryptexはロシア語と英語です。日本語・中国語・韓国語・スペイン語・アラビア語などの主要言語に最初からネイティブ対応する製品は存在せず、これは非英語圏ユーザーへの明確な差別化ポイントです。Otedamaの「主要10言語人間レビュー＋1,000言語機械翻訳」は**方針であって現状ではありません**：
実装済みの範囲は10言語×15メッセージID（起動時ログのみ）で、機械翻訳による多言語展開は未着手です。
空白は依然として空白であり、埋める作業が残っています。

**第四の空白は、Stratum V2対応の家庭用ツール**です。Braiins OS+はStratum V2対応だがASIC限定、CGMinerは対応が不完全、NiceHashは独自プロトコル中心です。「家庭ユーザーが使えるStratum V2ネイティブクライアント」は未充足であり、Bitcoin Core v30がStratum V2を公式サポートしたこのタイミングで参入する戦略的価値は高いです。

**第五の空白は、Lightning Network決済の標準化**です。どの競合もLightning Network決済を中核機能として組み込んでおらず、オンチェーン決済の手数料負担と遅延が、小規模マイナーの実質収益を圧迫しています。Lightning Networkでの即時・低手数料決済を標準実装する製品は市場で未充足です。

## Otedamaの設計への翻訳

以上の分析から、Otedamaの設計に反映すべき具体的な改善点が導かれます。

**この節は session 266 に書き直しました。** それ以前は、未実装の項目を含めて全てが現在形で
書かれており、競合の弱点を「Otedamaは既にこう埋めている」と読める文章になっていました。
競合分析でそれをやると、比較表の片側だけが願望になります。以下は**実装済み（参照つき）／
スコープ済み**を明示的に分けた記述です。

**設定不要の起動 — 実装済み、ただし但し書きあり。** `otedama run --bitcoin-address bc1q...`
の一行でハードウェア自動検出（`internal/hal`）、Lightning ウォレット自動生成
（`internal/lightning`）、稼働開始まで到達します。**プールの「自動選択」は実装していません**：
プール未設定時のフォールバックは `config.DefaultPoolURL` という単一の組み込み定数であって
推薦リストではなく、しかもそのホストは現在解決しません（`docs/KNOWN_LIMITATIONS.md` §20）。
つまり本項の空白は**まだ完全には埋まっていません**。

**秘密鍵をユーザーデバイス上のみに保持 — 実装済み。** シードは端末上で生成され、
AES-256-GCM + scrypt で暗号化して保存されます（`internal/lightning/seedstore.go`）。
サーバーは存在せず、メンテナが鍵に触れる経路もありません。`otedama wallet verify` で
バックアップの復元可能性を、`otedama wallet change-passphrase` でパスフレーズ更新を、
どちらも端末内で実行できます。**ZKP 認証は未実装**で v4.0 スコープです — KYC を代替する
仕組みとして計画されていますが、現時点の非カストディ性は ZKP ではなく「預からない」構造から
来ています。

**多言語 — 部分的。** メッセージカタログは10言語（en/ja/zh/ko/es/fr/de/pt/ru/ar）実在し、
完全性・プレースホルダ一致・テンプレート解析をテストが強制します（`internal/i18n/messages/`）。
**ただし範囲は15メッセージIDで、消費するのは起動時のログ行だけです。** TUI ダッシュボード、
`doctor`、`wallet` の各出力は英語のみです。「ドキュメントの全てが対応言語で表示される」は
以前の記述の誤りで、日本語と英語のドキュメントは併存しますが、他8言語は未整備です。
競合との差分としては依然有効ですが、その差分は現状「起動時メッセージの10言語化」の大きさです。

**プール選択の透明性 — 実装済み（UI は無い）。** 任意の Stratum V1/V2 プールを
`config.yaml` の `pools:` に順序つきで並べられ、先頭から順に failover します
（`internal/engine/run.go`）。組み込みの推薦リストは持たず、プール運営者との利益相反はありません。
**「直感的な UI」は存在しません** — 設定手段は設定ファイル、環境変数、フラグの三層です。

**三層セキュリティレビュー — 制度としては定義済み、CI での強制は不完全。** 方針は CLAUDE.md に
あり、gosec・CodeQL・Semgrep・Trivy はワークフローに存在します。一方で
`staticcheck` と `govulncheck` はどのワークフローでも実行されておらず、Actions の SHA ピン留めと
リリース署名も未実施です（§21）。ファズ target は Stratum フレーム解析に2本ありますが、CI で
`-fuzz` を回すジョブはありません。CVE-2014-4501〜4503 のような欠陥を防ぐ体制として数えるには、
まだ埋めるべき穴があります。

## 当初の実装順序と、実際に出来上がったもの

以下は本書が最初に立てた五つの優先事項と、その後の実装がどう着地したかです
（session 266 に追記。**計画をそのまま残して結果を併記します** — 計画を結果に合わせて
書き換えると、外れた予測が履歴から消えてしまうため）。

第一優先は**ハードウェア自動検出ロジック**でした。→ **実装済み**（`internal/hal`。CPU は常時、
Linux は sysfs 経由で GPU も検出）。ただし検出した GPU は採掘に使えません — CUDA/ROCm/Vulkan の
ディスパッチが無いためです（§4）。

第二優先は**設定ファイル非依存の起動経路**でした。→ **実装済み**（`internal/config` の4層解決:
デフォルト → ファイル → 環境変数 → フラグ。優先順位はテストで固定）。

第三優先は**多言語メッセージ基盤**でした。→ **実装済み、ただし当初案とは別物**。
`golang.org/x/text` の `message` パッケージは**使っていません**。外部依存ゼロの方針
（ADR-003）に沿って `internal/i18n/messages/` に自前のカタログを持ち、完全性・プレースホルダ一致・
テンプレート解析をテストで強制しています。**CLDR 準拠の複数形処理は実装していません**し、
プロパティベーステストでもなく通常のテーブル駆動テストです。範囲は15メッセージID。

第四優先は**Stratum V2メッセージパーサー**でした。→ **実装済み**
（`internal/stratum`）。ただし**SRI の公式テストベクトルを golden file として取り込んではいません**。
検証は仕様書の記述との突き合わせ（session 256）と、フレーム解析の fuzz target 2本によっています。
ベクトル取り込みは残った改善点です。

第五優先は**Lightning Wallet自動生成**でした。→ **実装済み、ただし LDK は使っていません**。
BIP-39 のシード生成と AES-256-GCM + scrypt での保管を標準ライブラリ＋`golang.org/x/crypto` で
行っており、Lightning ノードそのものは実装していません（受取専用、§6）。「秘密鍵は端末上のみ」の
不変条件はテストで強制されています。

残っている改善点は `docs/KNOWN_LIMITATIONS.md` に番号つきで、優先順位は
`docs/CATEGORY_AUDIT.md` の最新セッション項に記載しています。
